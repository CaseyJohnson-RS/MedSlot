# 0004. Нарушения и бан вычисляются из истории записей

- **Статус:** Принято
- **Дата:** 2026-10-30

## Контекст

После 3 нарушений пациенту временно запрещается онлайн-запись. Хранить счётчик в `Patient` значит обновлять два агрегата в транзакции перехода статуса записи (или делать это асинхронно через событие и получить окно, в котором бан ещё не применён). Счётчик со скользящим окном к тому же нужно «уменьшать» со временем.

## Решение

Отдельного счётчика нет. Нарушения — это записи пациента в статусах `LateCancelled` и `NoShow`; бан вычисляется доменной политикой `PatientBookingPolicy` по датам нарушений, текущему времени и `BanOverride` пациента. Правила — [domain.md, §7](../domain.md#7-нарушения-и-бан).

Для запроса нужен индекс `(patient_id, status, status_changed_at)`.

## Рассмотренные варианты

- **Счётчик в `Patient`, обновляемый в той же транзакции.** Два агрегата в транзакции, сложное скользящее окно. Отклонено.
- **Счётчик, обновляемый консьюмером событий.** Eventually consistent: между нарушением и баном пациент успевает записаться. Отклонено.

## Последствия

- Бан всегда согласован с историей, нет данных для рассинхронизации.
- Проверка бана — дополнительный запрос при каждой записи пациента; при необходимости кэшируется.
- Снятие бана админом — запись `BanOverride` с моментом снятия, история не меняется.
