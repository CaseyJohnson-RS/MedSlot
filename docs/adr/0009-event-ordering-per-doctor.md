# 0009. Порядок событий по врачу

- **Статус:** Принято
- **Дата:** 2026-10-30

## Контекст

Консьюмерам важен порядок: если `AppointmentCancelled` придёт раньше `AppointmentBooked`, уведомления отправят «запись отменена» до «вы записаны», а проекция расписания окажется неверной. Kafka гарантирует порядок только внутри партиции. Кроме того, порядок может сломаться ещё до Kafka, на стороне публикатора:
1. несколько экземпляров relay читают outbox параллельно и публикуют вперемешку;
2. событие не опубликовалось, а следующее событие того же врача ушло, и при повторе первое окажется после второго;
3. продюсер повторяет отправку после сетевого сбоя и может переставить сообщения в партиции.

## Решение

- **Ключ сообщения — `doctorId`.** Все события врача идут в одну партицию топика `appointments` (6 партиций). Записи к одному врачу — естественная единица порядка: расписание, лист ожидания, уведомления.
- **Один активный relay.** Лидер держит `pg_try_advisory_lock` на отдельном соединении без пула. При падении процесса Postgres закрывает сессию и снимает блокировку, при штатной остановке соединение закрывается. Соединение из пула для этого не подходит: Npgsql сбрасывает сессию только при следующем использовании, и блокировка повисла бы (это поймал тест).
- **Строгий порядок внутри relay.** Публикация по одной в порядке `id` с ожиданием подтверждения. Если событие врача не опубликовалось, следующие события **этого же врача** в итерации пропускаются, а события других врачей идут дальше.
- **Идемпотентный продюсер** (`enable.idempotence=true`, `acks=all`): повтор после сбоя не создаёт дубль и не меняет порядок в партиции.

## Рассмотренные варианты

- **Ключ — `appointmentId`.** Больше параллелизма, но события разных записей одного врача (освобождение слота и предложение его из листа ожидания) могут прийти в обратном порядке. Отклонено.
- **Несколько relay с разделением по ключам** (хэш `doctorId` по экземплярам). Масштабируется, но сложнее и требует координации при смене числа экземпляров. Для текущей нагрузки не нужно.
- **Пакетная асинхронная публикация с ожиданием в конце.** Быстрее, но при ошибке в середине пакета следующие сообщения того же ключа уже могли уйти. Отклонено ради простоты гарантий.

## Последствия

- Порядок гарантирован для событий одного врача от одного публикатора. Порядок между врачами не гарантирован и не нужен.
- Пропускная способность ограничена одним relay и синхронной публикацией. Это сотни событий в секунду, для клиники с запасом.
- `id` в outbox выдаётся при вставке, а не при коммите, поэтому параллельные транзакции могут закоммититься не по порядку `id`. Для одного врача это исключено: новые записи сохраняются под advisory-блокировкой врача (ADR 0005), а изменения одной записи сериализует `xmin`.
- Проверено тестами: три события врача приходят в одну партицию по возрастанию offset; при недоступной Kafka события ждут в outbox и доставляются по порядку; сбой по одному врачу не задерживает других.
