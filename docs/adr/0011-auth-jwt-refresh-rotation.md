# 0011. JWT и ротация refresh-токенов

- **Статус:** Принято
- **Дата:** 2026-10-30

## Контекст

До фазы 7 пациент передавался в теле запроса, и любой мог записаться или отменить запись от чужого имени. Нужны вход, роли (пациент, врач, администратор) и проверки «только своё». API без состояния, у клиентов (веб, мобильное приложение) сессии длиной в недели. Короткий access-токен безопасен, но заставлял бы входить заново каждые 15 минут. Длинный токен опасен при утечке.

## Решение

**Access-токен** — JWT (HMAC-SHA256), живёт 15 минут. Claims: `sub` (учётная запись), `role`, `patient_id` или `doctor_id`. Персональных данных в токене нет. Срок жизни проверяется по `IClock` приложения: одни и те же часы при выпуске и проверке.

**Refresh-токен** — 32 случайных байта, живёт 30 дней, в БД хранится только SHA-256.
- **Одноразовый.** `/auth/refresh` гасит токен и выдаёт новую пару.
- **Семейство.** Все токены одного входа связаны `family_id`, разные входы (телефон, ноутбук) — разные семейства.
- **Обнаружение повтора.** Если предъявлен уже погашенный токен, им воспользовались дважды: значит, он утёк. Отзывается всё семейство, и войти заново придётся и злоумышленнику, и владельцу. Другие входы пользователя не затрагиваются.
- **Двойной клик.** Два одновременных обновления одним токеном решает `xmin`: второе получает отказ без отзыва семейства. Это гонка клиента, а не утечка.

**Пароли** — PBKDF2 (HMAC-SHA512, 100 000 итераций) из ASP.NET Core Identity. Формат хэша версионирован, устаревшие хэши пересчитываются при входе. На неизвестный email пароль всё равно проверяется против фиктивного хэша: время ответа не выдаёт, какие адреса зарегистрированы. На вход и регистрацию действует лимит частоты по IP.

**Права:**

| Действие | Пациент | Врач | Администратор |
|---|---|---|---|
| Расписание, слоты | ✓ без входа | ✓ | ✓ |
| Записаться, отменить свою, лист ожидания | ✓ (из токена) | — | — |
| Запись за пациента (без бана и лимита) | — | — | ✓ |
| Посмотреть запись | свою | свой приём | любую |
| Отмена клиникой, «состоялся», неявка | — | свои приёмы | любые |
| Расписание врача, снятие бана, учётные записи сотрудников | — | — | ✓ |

Чужая запись или предложение отвечают 404, а не 403: не раскрываем, что такой id существует. Список данных другого пациента отвечает 403.

Ключи идемпотентности и лимит частоты записи привязаны к `sub` (ADR 0007).

## Рассмотренные варианты

- **Внешний провайдер (Keycloak, Auth0).** Правильно для продакшена с SSO, но для pet-проекта это отдельная инфраструктура, и механизм ротации остался бы скрыт. Схема claims совместима: переход меняет только выпуск токенов.
- **Cookie-сессии.** Проще отзывать, но API рассчитан на мобильных клиентов, а cookie требуют защиты от CSRF.
- **Долгоживущий access-токен без refresh.** Утечка дала бы доступ на весь срок без возможности отзыва. Отклонено.
- **Хранить refresh-токен в открытом виде.** Утечка БД дала бы доступ ко всем сессиям. Отклонено.

## Последствия

- Отозвать access-токен нельзя: после выхода он живёт до 15 минут. Это осознанная цена stateless-проверки.
- Ключ подписи симметричный и общий для выпуска и проверки. При выделении сервисов (внутренний API в фазе 7.2) понадобится асимметричная подпись или отдельный сервисный ключ.
- Таблица `refresh_tokens` растёт. Удаление истёкших — вместе с остальной чисткой данных.
