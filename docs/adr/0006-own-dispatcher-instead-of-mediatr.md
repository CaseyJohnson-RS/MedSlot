# 0006. Обработчики без MediatR

- **Статус:** Принято
- **Дата:** 2026-10-30

## Контекст

Прикладному слою нужны команды и запросы с обработчиками и сквозная логика вокруг них: логирование, позже валидация и метрики. Привычное решение — MediatR, но с 2025 года он распространяется под коммерческой лицензией. Кроме того, отправка через `mediator.Send(...)` скрывает зависимость: по сигнатуре эндпоинта не видно, какой обработчик он вызывает.

## Решение

Минимальный набор своих абстракций в `MedSlot.Application.Abstractions`:

- `ICommand<TResponse>` / `IQuery<TResponse>` — маркеры;
- `ICommandHandler<TCommand, TResponse>` / `IQueryHandler<TQuery, TResponse>` возвращают `Result<TResponse>`;
- `Unit` — для команд без результата.

Посредника нет: эндпоинт внедряет `ICommandHandler<BookAppointment, AppointmentId>` напрямую. `AddApplication()` находит обработчики сборки рефлексией и регистрирует каждый обёрнутым в логирующий декоратор. Декоратор пишет только имя операции, исход и длительность: в командах есть персональные данные.

## Рассмотренные варианты

- **MediatR.** Коммерческая лицензия, неявные зависимости. Отклонено.
- **Scrutor для декораторов.** Ещё одна зависимость ради двадцати строк регистрации. Отклонено.
- **Source generator** (как у Mediator). Быстрее рефлексии при старте, но сложнее читать. Для текущего числа обработчиков выигрыша нет. Можно вернуться позже.

## Последствия

- Зависимости эндпоинтов явные, переход к коду обработчика работает в IDE.
- Новый декоратор (валидация, метрики) добавляется одной строкой в `AddApplication()`.
- Обработчики `internal`: снаружи сборки доступны только команды и интерфейсы.
- Порядок декораторов задаётся явно при регистрации, без конвейера.
