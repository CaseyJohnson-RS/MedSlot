# MedSlot — план работ

Оценки даны из расчёта ~10–15 часов в неделю. Каждая фаза заканчивается рабочим, протестированным состоянием и коммитом в `main` — проект можно показывать после любой из них.

Общая оценка: **12–16 недель** до полного объёма, **~6 недель** до показываемого MVP (фазы 0–4).

---

Зафиксировано в [domain.md](domain.md) и ADR 0002–0004.

- [x] **Статусы записи:** `Held`, `Booked`, `Released`, `Cancelled`, `LateCancelled`, `Completed`, `NoShow`; `Confirmed` убран ([ADR 0002](adr/0002-appointment-status-model.md)).

- [x] **Пересечения у пациента** запрещены вторым exclusion constraint.

- [x] Повтор POST с тем же ключом → тот же ответ, одна запись в БД.
- [x] 10 параллельных запросов с одним ключом → одна запись, остальные — сохранённый ответ или 409.

## Фаза 4. Transactional Outbox + Kafka (1–2 недели) — ✅ готово, MVP

### Задачи
- [x] Таблица `outbox_messages (id identity, event_id, event_type, partition_key, envelope jsonb, trace_parent, occurred_at, published_at, attempts, last_error)`; частичный индекс по неопубликованным.
- [x] `SaveChanges`-интерсептор: доменные события агрегатов → строки outbox в той же транзакции.
- [x] Проект `MedSlot.Contracts` (только BCL): `EventEnvelope` (`eventId`, `eventType`, `schemaVersion`, `occurredAt`, `aggregateId`, `doctorId`, `traceparent`, `payload`) и payload v1 восьми событий. **Без ПДн** — только id и время.
- [x] `OutboxRelay` + фоновая служба:
  - единственный активный экземпляр — `pg_try_advisory_lock` на соединении без пула;
  - публикация по одной в порядке `id` с ожиданием подтверждения, отметка `published_at`;
  - при ошибке — события того же врача в итерации пропускаются, остальные идут дальше;
  - экспоненциальная пауза при ошибках (до 30 с). Метрики лага — в фазе 8.
- [x] Kafka producer: `enable.idempotence=true`, `acks=all`, ключ = `doctorId`, короткий `message.timeout.ms`; заголовки `event-id`, `event-type`, `schema-version`, `traceparent`.
- [x] Топики `appointments` (6 партиций) и `appointments.dlt` создаются при старте в Development и в тестах.
- [x] Очистка опубликованных событий старше 7 дней.
- [x] `/health/ready` проверяет Kafka.

### Тесты (Testcontainers Postgres + Kafka, 7 тестов)
- [x] Бронирование → событие в Kafka с ключом, заголовками и конвертом; ПДн в сообщении нет.
- [x] Откат транзакции → события нет.
- [x] События врача приходят в одну партицию по порядку.
- [x] Kafka недоступна → события ждут в outbox с отметкой о попытке, затем доставляются по порядку.
- [x] Сбой публикации по одному врачу не задерживает других и не даёт его событиям обогнать друг друга.
- [x] Два relay → активен один; после остановки первого лидером становится второй.
- [x] Очистка опубликованных по сроку хранения.

**Итог:** события доставляются at-least-once с сохранением порядка по врачу; проверено на стеке docker-compose (запись и отмена через HTTP → два события в Kafka).

## Фаза 6. Лист ожидания (1 неделя) — ✅ готово

### Задачи
- [x] `WaitlistEntry`: пациент, врач, услуга, диапазон дат, позиция в очереди (`QueuedAt`), статус; после отказа или пропуска — в конец очереди.
- [x] Предложение делается **в той же транзакции**, что и освобождение слота (отмена пациентом, отказ, истечение, выход из очереди): обычная запись не может перехватить время между шагами. Отмена клиникой предложения не создаёт.
- [x] Удержание `Held` с `HoldExpiresAt` защищено тем же exclusion constraint.
- [x] Эндпоинты: встать в очередь, выйти, принять, отказаться, заявки пациента с текущим предложением.
- [x] Фоновая служба истечения: просроченные удержания по одному, каждое в своей транзакции; заявки с прошедшими датами закрываются. Вместо `FOR UPDATE SKIP LOCKED` — оптимистичная блокировка (`xmin`) записи и заявки: изменения идут через общий `UnitOfWork`.
- [x] События `WaitlistSlotOffered`, `WaitlistOfferAccepted`, `WaitlistOfferDeclined`, `WaitlistOfferExpired` (уже обрабатываются воркерами уведомлений и аудита).
- [x] Пациент с баном не получает предложений и не может встать в очередь; занятый в это время пациент и неподходящая услуга пропускаются.

### Тесты (12 доменных, 13 интеграционных)
- [x] Отмена → первый в очереди получает `Held`; посторонний не может забронировать этот слот.
- [x] Принятие → запись; отказ → следующему, отказавшийся — в конец очереди.
- [x] Таймаут → предложение переходит второму; принятие после истечения → отказ.
- [x] Параллельные принятие и истечение → один побеждает, состояние согласовано.
- [x] Отмена клиникой и слишком поздняя отмена → предложения нет; выход из очереди с предложением → следующему.
- [x] Правила постановки: дубль, лимит заявок; заявки с прошедшими датами закрываются; сценарий через HTTP.

**Итог:** цикл «отмена → предложение → уведомление → принятие» проверен на стеке docker-compose.
